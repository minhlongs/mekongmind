## STEP 1: PLAN — 10 Edge Case Fixes

Based on deep code analysis of the repository, here's the actionable implementation plan organized by domain:

---

### 🔴 FIX 1 — PayOS: Race Condition in IPN Idempotency
**File:** `src/app/api/payos/ipn/route.ts` (lines 64–93)

**Problem:** The idempotency check is a two-step dance:
1. `INSERT` into `payos_events` (relies on UNIQUE constraint to detect duplicate)
2. If INSERT fails → `SELECT` to check `processed` flag → return

Between step 1's failure and step 2's SELECT, a **second concurrent webhook** could INSERT the same `event_id` (succeeding) and start processing. The first webhook then reads `processed: 0` and proceeds to double-process.

**Fix:** Replace the two-step with a single atomic `INSERT OR IGNORE` + immediate SELECT, or use `INSERT ... ON CONFLICT DO NOTHING RETURNING processed`.

---

### 🔴 FIX 2 — PayOS: Underpayment Handling & Order Probing
**File:** `src/app/api/payos/ipn/route.ts` (lines 160–172)

**Problem:**
- Amount check happens AFTER order lookup → attacker can probe for valid `paymentLinkId`/`orderCode` values by sending crafted IPNs with wrong amounts.
- No handling for overpayments (user pays more than expected) — silently accepted but no credit issued.
- No handling for underpayments — rejected with 400 but order stays in `pending` forever (no partial-fulfillment path).

**Fix:** Move amount validation before order lookup (constant-time compare). Add overpayment refund flag + underpayment alert.

---

### 🔴 FIX 3 — PayOS: Insecure Fallback in Batch Failure Path
**File:** `src/app/api/payos/ipn/route.ts` (lines 213–219)

**Problem:** When the D1 batch fails, the fallback runs individual `db.from()` Supabase calls **without** verifying that the batch actually committed partially. If the batch succeeded partially (e.g., subscription updated but order not marked complete), the fallback re-runs and creates inconsistency. Also the Supabase client (`db`) may be a different connection than `d1` (the raw D1), leading to **read-your-writes** violations.

**Fix:** After batch failure, query the actual state before applying fallback mutations. Use a single `getD1Raw()` throughout the handler.

---

### 🔴 FIX 4 — Auth: Admin Demotion Bypass via Stale Middleware Tier Check
**File:** `src/middleware.ts` (lines 164–191)

**Problem:** The middleware checks `tier === 'MASTER'` from the `subscriptions` table, but:
- It reads only the latest row (`ORDER BY created_at DESC LIMIT 1`) — if a downgrade is in progress, the old row might still show MASTER.
- It does NOT check `user_roles` or any RBAC table — a user with MASTER tier but revoked admin role would still pass.
- The `getD1Raw()` call may use a cached/stale binding in edge runtime.

**Fix:** Add a `user_roles` check (`role = 'admin'`) as a second gate. Add a `status = 'active'` filter to the subscription query. Ensure the D1 query is not cached.

---

### 🔴 FIX 5 — Auth: MFA Fail-Open in `isSessionMfaPending`
**File:** `src/seed/auth/mfa/login-challenge.ts`

**Problem:** The middleware catches MFA check errors and fails closed (good), but the `isSessionMfaPending` function likely has a fail-open path where a database error returns `false` (no MFA pending) instead of throwing. Need to verify the implementation.

**Fix:** Ensure `isSessionMfaPending` throws on DB errors rather than returning `false`. Add a defensive check in the middleware for `null`/`undefined` session IDs.

---

### 🔴 FIX 6 — Video: HeyGen Duplicate CAS in Retry/Webhook Race
**File:** `src/land/fulfillment/complete-video-from-webhook.ts`

**Problem:** The CAS functions (`recordAttemptCAS`, `markWebhookPermanentFailureCAS`) guard against double-counting, but the `completeVideoFromWebhook` function (success path, line 121–134) uses:
```sql
WHERE id = ?1 AND status != 'completed' AND status != 'failed_permanent'
```
This is a CAS, but there's a subtle race: if the **retry cron** marks the video as `failed` (incrementing attempt_count) at the same time the webhook marks it as `completed`, both can succeed because they check different status values. The result: video is `completed` but `attempt_count` was incremented unnecessarily, and the circuit breaker sees a phantom failure.

**Fix:** Add an `AND attempt_count < MAX_ATTEMPTS` guard to the success CAS. The retry cron should also check `status = 'processing'` (not just `!= 'completed'`).

---

### 🔴 FIX 7 — Video: TOCTOU Race in Optimistic Lock (cost-guardrail → deduct)
**Files:** `src/land/video/cost-guardrail.ts` + `src/land/mcu/credits-repo.ts`

**Problem:** Classic Time-of-Check-Time-of-Use:
1. `checkVideoBudget()` reads `credits_remaining` → says "allowed"
2. Two concurrent requests both pass the guardrail
3. Both call `deductCredits()` — the `WHERE credits_remaining >= ?` prevents overdraft, but both succeed if balance was sufficient for one, resulting in one request being billed and the other failing silently (or worse, both succeed if the balance was exactly 2x).

**Fix:** Combine the check-and-deduct into a single atomic D1 statement: `UPDATE ... SET credits_remaining = credits_remaining - ? WHERE user_id = ? AND credits_remaining >= ? RETURNING credits_remaining`. Check the returned value to confirm success.

---

### 🔴 FIX 8 — Cron: Timeout & Double-Execution Guard
**File:** `src/land/cron/run-tracker.ts` (lines 52–78)

**Problem:**
- `wasRecentlyRun()` **fails open** (returns `false` on DB error) — if D1 is temporarily unavailable, the cron fires again, potentially double-processing.
- No maximum execution time guard — a cron that hangs won't be killed.
- No "stale lock" detection — if a cron crashes mid-execution, `last_run_at` is never updated, so `wasRecentlyRun` won't help.

**Fix:** Make `wasRecentlyRun` fail closed (return `true` on error). Add a `started_at` column with a TTL (e.g., 2x expected duration) to detect stuck crons. Add `recordCronRun` at the START of execution (not just end) with status `'running'`.

---

### 🔴 FIX 9 — Metering: Redis Non-Atomic Pipeline Increment
**File:** `src/forest/usage-metering/realtime-tracker-kv-ops.ts` (lines 42–69)

**Problem:** The `incrementRealTimeUsage` function uses `kv.pipeline()` with `hincrby` + `expire`. The Upstash Redis REST API executes pipeline commands sequentially over HTTP — if the connection drops after `hincrby` succeeds but before `expire`, the key is incremented but without TTL, causing ghost credits. Also, the error fallback re-throws, but the caller (`trackWithCircuitBreaker`) records a circuit failure — making the system think credits weren't consumed when they actually were.

**Fix:** Use a Lua script via `kv.eval()` for atomic increment+expire. On error, read the current value to determine if the increment partially succeeded before recording the circuit failure.

---

### 🔴 FIX 10 — Metering: D1 Rollup Missing Upsert + Timezone Handling
**File:** `src/forest/usage-metering/rollup/daily-rollup.ts` (lines 16–47)

**Problem:**
- `upsertDailySummary` uses `insert()` which **fails on duplicate** `(day_timestamp, tenant_id, license_nonce)` — if the rollup runs twice for the same day, the second run errors out.
- `day_timestamp` is computed as `Math.floor(now / 86400) * 86400` — this uses **local time** of the server, not UTC. A server in a non-UTC timezone would create rollup days that don't align with calendar days.
- No retry logic — if D1 is briefly unavailable, the rollup fails silently.

**Fix:** Replace `insert()` with `upsert()` (using `ON CONFLICT DO UPDATE`). Use UTC epoch for `day_timestamp`. Add retry with backoff.
