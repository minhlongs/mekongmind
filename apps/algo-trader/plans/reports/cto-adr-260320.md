## Executive Summary

**Target:** < 100ms end-to-end latency cho cross-exchange arbitrage (Binance/OKX/Bybit)

**Decision:** Event-Driven Monolith với hybrid architecture — lowest latency cho MVP, dễ evolution sang microservices sau.

**Infrastructure Cost:** $60-120/month (VPS AWS Singapore + Tokyo)

### Compliance Requirements

- Trade history retention: **7 years** (audit trail)
- API keys: **Never in codebase** — .env only
- P&L tracking: **Daily snapshots** (tax reporting)

## 2. Latency Budget Breakdown

### Target: < 100ms (End-to-End)

| Component | Budget | % Total | Notes |
|-----------|--------|---------|-------|
| **Data Ingestion** | 5-15ms | 5-15% | WebSocket tick → normalization |
| **Signal Detection** | 10-25ms | 10-25% | Spread calc + scoring + regime check |
| **Order Book Validation** | 10-20ms | 10-20% | L2 depth + slippage calculation |
| **Risk Circuit Breaker** | 2-5ms | 2-5% | Health check + trip count + exposure |
| **Order Execution** | 15-40ms | 15-40% | Atomic order placement (Promise.allSettled) |
| **Exchange Round-Trip** | 20-50ms | 20-50% | Network latency to exchange API |
| **Buffer/Safety Margin** | 10-15ms | 10-15% | Jitter, GC pauses, OS scheduling |

### Critical Path Analysis

```
Best Case: 5 + 10 + 10 + 2 + 15 + 20 + 10 = 72ms ✅
Typical:   10 + 18 + 15 + 3 + 25 + 35 + 12 = 118ms ⚠️
Worst Case: 15 + 25 + 20 + 5 + 40 + 50 + 15 = 170ms ❌

Kết luận: Để đạt sub-100ms P95, cần:
- VPS colocation gần exchange servers (giảm network RTT xuống < 15ms)
- Event-driven architecture (không polling!)
- Pre-computed signals + lazy validation
- Order execution phải < 25ms (optimized HTTP client, connection pooling)
```

## 3. Architecture Decision

### Selected: Hybrid Event-Driven Monolith

```
┌─────────────────────────────────────────────────────────────┐
│                    MONOLITH (Node.js)                       │
│                                                             │
│  ┌──────────────────────────────────────────────────────┐  │
│  │              EVENT BUS (EventEmitter)                │  │
│  └──────────────────────────────────────────────────────┘  │
│           │                │                 │               │
│           ▼                ▼                 ▼               │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐      │
│  │  WebSocket   │  │   Signal     │  │   Order      │      │
│  │  Listeners   │  │  Detectors   │  │  Executor    │      │
│  └──────────────┘  └──────────────┘  └──────────────┘      │
│                                                             │
│  ┌──────────────────────────────────────────────────────┐  │
│  │         IN-MEMORY STATE (Map/Cache)                  │  │
│  │  - Latest prices per exchange:symbol                 │  │
│  │  - Order book snapshots (L2, 10 levels)              │  │
│  │  - Position tracking                                 │  │
│  └──────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

### Why NOT Microservices?

| Criterion | Microservices | Monolith | Winner |
|-----------|---------------|----------|--------|
| **Latency** | gRPC adds 5-15ms/hop | In-process < 1ms | Monolith |
| **Complexity** | K8s, service mesh | Single binary | Monolith |
| **Scalability** | Independent scaling | Vertical only | Microservices |
| **Debugging** | Distributed tracing | Stack traces | Monolith |
| **MVP Fit** | ❌ Overkill | ✅ Simple | Monolith |

### Why NOT Pure Event-Driven?

| Criterion | Event-Driven | Hybrid | Winner |
|-----------|--------------|--------|--------|
| **Latency** | Sub-10ms reaction | Sub-10ms | Tie |
| **Complexity** | Event schema overhead | In-process events | Hybrid |
| **Scalability** | Easy horizontal | Easy evolution | Hybrid |
| **Debugging** | Hard (distributed) | Stack traces | Hybrid |

## 4. Tech Stack Decisions

### 4.1 Exchange API: CCXT vs Direct

| Metric | CCXT | Direct API | Winner |
|--------|------|------------|--------|
| **REST overhead** | +5-15ms | Baseline | Direct |
| **WebSocket** | +2-5ms (wrapper) | Baseline | Direct |
| **Initial dev time** | 1-2 days | 1-2 weeks/exchange | CCXT |
| **Maintenance** | Auto (npm update) | Manual changelog tracking | CCXT |
| **Exchange coverage** | 100+ exchanges | 1 exchange = 1 codebase | CCXT |

**Decision:** ✅ **CCXT cho MVP**

**Rationale:**
- 10x faster development (days vs weeks)
- Multi-exchange arbitrage ready out-of-box
- Overhead negligible cho arbitrage (spread >> latency)
- Có thể optimize critical paths sang direct WebSocket sau

**Exception:** Dùng Direct API nếu:
- HFT (< 10ms latency requirement)
- Single exchange only
- Custom order types not supported by CCXT

### 4.2 Redis Data Structures (CHI TIẾT)

#### Orderbook State: ✅ Sorted Sets

```redis
# Orderbook: BNB/USDT bids
ZSET orderbook:BNB/USDT:bids
  - key = price (score, inverted for descending)
  - value = quantity (member metadata)
  - example: ZADD orderbook:BNB/USDT:bids 0.25 "450.50:1.5"

# Top of book: O(1)
ZRANGE orderbook:BNB/USDT:bids 0 0 WITHSCORES

# Best 10 levels: O(log N)
ZRANGE orderbook:BNB/USDT:bids 0 9 WITHSCORES

# Update level: O(log N)
ZADD orderbook:BNB/USDT:bids 0.25 "450.50:2.0"

# Remove stale: O(log N)
ZREM orderbook:BNB/USDT:bids "450.50:1.5"
```

**Why NOT Hashes:**
- Hashes: O(1) lookup nhưng không có ordering → không thể lấy "top 10 bids"
- Sorted Sets: O(log N) lookup + ordered by price → perfect cho orderbooks

**Why NOT Strings:**
- Strings: Full serialization/deserialization mỗi update
- No partial updates → high memory churn

---

#### Ticker Cache: ✅ Hashes (1 key per ticker)

```redis
# Structure: Hash with field per attribute
HSET ticker:BNB/USDT {
  "symbol": "BNB/USDT",
  "last": "450.50",
  "bid": "450.45",
  "ask": "450.55",
  "high": "460.00",
  "low": "440.00",
  "volume": "125000",
  "timestamp": "1710892800000"
}

# Get all: O(N) where N = fields
HGETALL ticker:BNB/USDT

# Get specific: O(1)
HMGET ticker:BNB/USDT last bid ask

# Update single field: O(1)
HSET ticker:BNB/USDT last "450.52"
```

**Anti-pattern (NOT recommended): Separate keys**
```redis
# ❌ 1 key per field
SET ticker:BNB/USDT:last "450.50"
SET ticker:BNB/USDT:bid "450.45"
# Problem: 10x memory overhead, no atomic multi-get
```

---

#### Trade History: ✅ Redis Streams

```redis
# Stream: append-only trade log
XADD trades:BNB/USDT * \
  id "trade_12345" \
  price "450.50" \
  quantity "1.5" \
  side "buy" \
  timestamp "1710892800000"

# Read latest 100: O(N)
XREVRANGE trades:BNB/USDT + - COUNT 100

# Consumer groups (cho multiple processors)
XREADGROUP GROUP processors:arb processors:consumer1 \
  COUNT 10 \
  STREAMS trades:BNB/USDT >

# Trim old trades (memory management)
XTRIM trades:BNB/USDT MAXLEN ~10000
```

**Why NOT List:**
- List: No metadata, no consumer groups, harder to trim by time
- Streams: Built-in consumer groups, ACK mechanism, time-based trimming

---

#### Pub/Sub Channels Design

```redis
# Channel naming convention
PUBLISH channel:orderbook:BNB/USDT <binary_delta>
PUBLISH channel:ticker:BNB/USDT <json_snapshot>
PUBLISH channel:trades:BNB/USDT <trade_event>
PUBLISH channel:signals:arb:BNB/USDT <arb_signal>

# Subscriber pattern
PSUBSCRIBE channel:orderbook:*      # All orderbooks
PSUBSCRIBE channel:signals:arb:*    # All arb signals
```

**Memory Optimization:**
```redis
# Use binary protocol cho orderbook deltas
# Protocol Buffers / MessagePack:
{
  "bids": [[450.50, 1.5], [450.45, 2.0]],
  "asks": [[450.55, 1.0], [450.60, 3.0]],
  "seq": 12345
}
# Size: ~100 bytes vs ~300 bytes JSON

# Compress with gzip cho large snapshots
# Use ZSTD cho better compression ratio
```

### 4.3 WebSocket vs REST Polling

#### Khi nào dùng WebSocket

| Data Type | Protocol | Reason |
|-----------|----------|--------|
| Orderbook | WebSocket | Real-time, 10-100ms updates |
| Trades | WebSocket | Real-time, event-driven |
| Ticker (24h stats) | WebSocket OR REST 1s | Có thể poll nếu latency OK |
| Funding rates | WebSocket OR REST 5s | Updates every 8h typically |

#### Khi nào REST Polling acceptable

| Data Type | Protocol | Polling Frequency |
|-----------|----------|-------------------|
| Account balance | REST | 1-5 seconds (or on-demand) |
| Open orders | REST | 500ms - 2 seconds |
| Order status | REST | On-demand after placement |
| Deposit/withdrawal | REST | 10-30 seconds |

#### Recommended Hybrid Architecture

```

│   - Bybit: wss://stream.bybit.com/v5/public/linear  │
│   Subscribe: orderbook, trades, ticker              │
├─────────────────────────────────────────────────────┤
```

## 7. Risk Mitigation

### Technical Risks

| Risk | Probability | Impact | Mitigation |
|------|-------------|--------|------------|
| **Exchange WS rate limit** | Medium | High | Smart throttling, multiple API keys |
| **Partial execution** | High | Medium | Rollback strategy, market hedge |
| **VPS outage** | Low | High | Dual-VPS failover |
| **Slippage > tolerance** | Medium | Medium | Pre-execution validation, abort |
| **Circuit breaker over-trip** | Low | Medium | Adaptive thresholds, regime-aware |

### Security Controls

| Control | Location | Description |
|---------|----------|-------------|
| **API Key Validation** | `src/middleware/license-validation.ts` | X-API-Key required |
| **Admin Auth** | `src/middleware/admin-auth.ts` | Separate admin key |

## 9. Unresolved Questions

1. **Exchange WebSocket Rate Limits:** Cần verify rate limits cụ thể cho mỗi exchange (OKX/Bybit/Binance) để tránh bị ban khi dùng event-driven.

2. **Atomic Execution Guarantee:** Nếu 1 leg fail sau khi leg kia đã execute, cần rollback strategy cụ thể (market hedge vs wait-and-see).

3. **Market Regime Detection Overhead:** Hurst exponent + volatility ratio calculation có thể thêm 5-10ms latency — cần benchmark thực tế.

4. **Failover Strategy:** Nếu VPS Tokyo fail, có auto-failover sang Singapore không? Hay dừng trading?

5. **Data Consistency:** Làm sao đảm bảo order book snapshot đồng bộ giữa các exchanges khi tính slippage?

6. **Compliance requirement:** How long must trade history be retained? (Currently assumed 7 years)

7. **Geographic distribution:** Need multi-region cho latency arbitrage beyond Asia?

8. **Volume projection:** Expected trades/day cho capacity planning?
